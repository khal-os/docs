A pack is a small git repository with a fixed shape. Every file has one job. Learning the shape once means you can read any `pack-*` repo later and know exactly where to look.

<Warning>
Pack/app repos are git-native. Do not add `.npmrc`, `publishConfig`, npm publish scripts/workflows, or `frontend.package` to new pack manifests.
</Warning>

## The tree

This is the layout you get when you scaffold a new pack with `khal new`:

```
.
├── khal-app.json          # Manifest (validated by @khal-os/types)
├── package/               # Frontend source and bundle inputs
│   ├── src/index.tsx      # Default export: React component
│   ├── tsup.config.ts
│   └── package.json       # Private build workspace, not a publish target
├── service/               # (Optional) backend pod
│   ├── src/index.ts       # Bun HTTP server + NATS subscription
│   ├── Dockerfile
│   └── healthcheck.sh
├── helm/                  # Optional Helm sub-chart for the service
│   ├── Chart.yaml
│   ├── values.yaml
│   └── templates/
└── .github/workflows/     # CI, policy checks, and optional backend artifact builds
```

## What each directory does

<AccordionGroup>
  <Accordion title="khal-app.json — the manifest" icon="file-json">
    The declarative contract between your pack and the KhalOS platform. It names the pack, lists permissions, declares services and windows, and points the platform at the frontend bundle source/path to load. The schema is enforced by `@khal-os/types` at build time, so a broken manifest fails CI before it can be installed.

    Every field — required and optional — lives in the [khal-app.json reference](/packs/khal-app-json).
  </Accordion>

  <Accordion title="package/ — the frontend workspace" icon="react">
    The React surface of your pack. `package/src/index.tsx` default-exports a component; `tsup.config.ts` produces CJS + ESM + `.d.ts` bundles; `package/package.json` supports local build tooling. It is a private workspace package, not a `pack-*` npm publish target.
  </Accordion>

  <Accordion title="service/ — the optional backend pod" icon="server">
    The long-running process for packs that need one — a Bun HTTP server, a NATS subscriber, a background worker. `service/src/index.ts` is the entry; `Dockerfile` is multi-stage; `healthcheck.sh` is a TCP probe used by Kubernetes. Delete the whole directory for frontend-only packs — CI will skip the Docker build automatically.
  </Accordion>

  <Accordion title="helm/ — the service's Helm sub-chart" icon="ship">
    A packaged Helm chart that deploys your `service/` image. `Chart.yaml` names the chart, `values.yaml` sets defaults (image repository, ports, resources), and `templates/` renders the Kubernetes objects. You don't hand-roll infrastructure — the chart is parameterized and the platform fills in the blanks.
  </Accordion>

  <Accordion title=".github/workflows/ — CI + release" icon="github">
    Workflows handle validation and optional release artifacts automatically:

    | Workflow | Trigger | What it does |
    |---|---|---|
    | `ci.yml` | Pull request | Lint, typecheck, build, test, manifest validation |
    | `ci-guards.yml` | Pull request | Secret scanning and pack-install policy checks |
    | `docker-build.yml` | Push/tag when service exists | Builds and pushes the backend service image |
    | `helm-release.yml` | Tag when chart exists | Packages the chart and pushes it to an approved OCI registry |

    There should be no workflow that publishes a `pack-*` frontend to npm.
  </Accordion>
</AccordionGroup>

## The contract in one sentence

**You declare the shape; the platform provides the runtime.** You write the manifest, the component, and (optionally) the service. The platform handles NATS connections, secrets, networking, installation, and deployment. That boundary is what keeps packs portable and the platform upgradeable.
