`khal-app.json` is the manifest every pack ships at its repo root. The platform reads it at install time and learns your pack's identity, permissions, frontend bundle path, and backend service (if any). The schema is defined by `@khal-os/types` and validated with Zod, so mistakes are caught at build time rather than in production.

<Warning>
Pack/app installs are git-native. New pack manifests should not declare npm package identity fields; use `bundlePath` for the built frontend bundle when needed.
</Warning>

## Required fields

Every pack manifest must declare these fields. The build will fail if any are missing or the wrong shape.

| Field | Type | What it is |
|---|---|---|
| `kind` | `"app" \| "service" \| "workflow"` | The manifest kind. Use `"app"` for user-facing packs. |
| `id` | `string` | Stable identifier — lowercase, hyphen-separated. Used for NATS subjects, install paths, and log lines. |
| `name` | `string` | Human-readable name shown in the launcher and window title. |
| `version` | `string` | Semantic version of the pack (`1.0.0`). Bumped on every release. |
| `icon` | `string` | Relative path to the pack icon (SVG recommended). |
| `description` | `string` | Short blurb shown in the launcher and the marketplace listing. |
| `author` | `string` | The name or organization shipping the pack. |
| `permissions` | `string[]` | The capabilities the pack needs (`nats:publish`, `files:read`, etc.). Declare the minimum — the platform enforces the list at runtime. |

<Callout type="info">
  Current `@khal-os/types` still accepts the legacy `frontend` object for backward compatibility, but `validatePackInstallPolicy` rejects package identity in pack/app repos. Public docs should teach the git-native policy: no package identity field in new pack manifests.
</Callout>

## Optional fields

These fields unlock additional pack shapes. You only declare what your pack needs.

| Field | When to use it |
|---|---|
| `bundlePath` | Relative path to the built ESM frontend bundle, such as `package/dist/index.mjs`. |
| `services[]` | Declare long-running processes your pack runs. Each entry names a process, its entry point, health check, and ports. |
| `windows[]` | Default window sizes and titles for the shell. Override per-view dimensions here. |
| `backend` | For packs that ship a container image — names the image, Helm chart, env vars, and ports. |
| `apps[]` | For bundle packs that ship multiple frontend apps in one repo. Follow the current bundle install contract and avoid per-app npm package identities in new manifests. |
| `sandbox` | For packs that require a per-user container on install. Declares CPU, memory, and volume mounts. |
| `defaultScope` / `allowedScopes` | Scopes the app supports at install time. Defaults are supplied by the schema, but explicit scopes make review easier. |

Every optional field has a deep dive in the exhaustive [khal-app.json schema reference](/reference/khal-app-json-schema) — bookmark it when you start declaring services or sandboxes.

## Worked examples

<Tabs>
  <Tab title="Frontend-only">
    The minimum viable manifest from a current `khal new`-style app: no backend, no services, one frontend bundle.

    ```json khal-app.json
    {
      "$schema": "https://raw.githubusercontent.com/khal-os/app-kit/dev/packages/types/src/khal-app-schema.json",
      "kind": "app",
      "id": "<name>",
      "name": "<Name>",
      "version": "1.0.0",
      "icon": "./package/src/assets/icon.svg",
      "description": "A KhalOS pack",
      "author": "KhalOS Core Team",
      "defaultScope": "user",
      "allowedScopes": ["user", "shared"],
      "permissions": [],
      "bundlePath": "package/dist/index.mjs"
    }
    ```

    Source: current git-native app policy and schema support for `bundlePath`.
  </Tab>

  <Tab title="Full-stack">
    A pack with both a frontend bundle and a backend service image. The `permissions` list names the capabilities the pack uses; the `backend` block points the platform at the container image and chart.

    ```json khal-app.json
    {
      "$schema": "https://raw.githubusercontent.com/khal-os/app-kit/dev/packages/types/src/khal-app-schema.json",
      "kind": "app",
      "id": "terminal",
      "name": "Terminal",
      "version": "1.0.0",
      "icon": "./package/src/assets/icon.svg",
      "description": "PTY terminal emulator for KhalOS with NATS-bridged stdin/stdout",
      "author": "KhalOS Core Team",
      "defaultScope": "user",
      "allowedScopes": ["user", "shared"],
      "permissions": ["pty:spawn", "nats:publish", "nats:subscribe"],
      "bundlePath": "package/dist/index.mjs",
      "backend": {
        "image": "ghcr.io/khal-os/pack-terminal-service",
        "helmChart": "oci://ghcr.io/khal-os/charts/pack-terminal",
        "env": {
          "KHAL_PTY_SHELL": "/bin/bash"
        },
        "ports": [8002]
      }
    }
    ```

    Source: the full-stack pattern updated for git-native installs.
  </Tab>
</Tabs>

## Permissions: declare the minimum

`permissions` is where you tell the platform what your pack intends to do. The platform enforces the list at runtime — a pack without `nats:publish` cannot publish to NATS, period.

<Callout type="warning">
  **Principle of least privilege.** Start with an empty `permissions` array and add entries only when the build surfaces a denied capability. Packs that over-declare permissions are flagged in review.
</Callout>

Common permissions include `nats:publish`, `nats:subscribe`, `files:read`, `files:write`, `pty:spawn`, `http:fetch`, `system:clipboard`, and `system:notifications`. The full list and the semantics of each lives in the [khal-app.json schema reference](/reference/khal-app-json-schema).

## Secrets: declare, don't embed

Never put secrets directly in `khal-app.json`. The manifest is committed to git and read as part of your pack. Instead, declare what your pack needs and let the platform provide the values at runtime — through the `backend.env` block for non-sensitive config or via the platform's secret store for credentials.

## Validation

The toolchain validates your manifest on every build. If a required field is missing, a type is wrong, or a permission name is unrecognized, you'll see a clear Zod error with the field path before the build proceeds. Policy checks also reject npm-publish metadata in pack/app repos.
