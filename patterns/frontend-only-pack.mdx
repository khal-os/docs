A **frontend-only pack** is the simplest shape a Khal pack can take. No `service/` directory, no Docker image, no Helm chart — just a React component bundled from the pack repo and loaded by the shell after git-native install. `pack-settings` is the reference implementation for this pattern, but older snapshots may still show npm-era fields that new packs must not copy.

<Callout type="warning">
  New packs are git-native. Do not add `.npmrc`, `publishConfig`, npm publish scripts/workflows, or `frontend.package` to `khal-app.json`.
</Callout>

## When to pick this shape

<CardGroup cols={2}>
  <Card title="Use frontend-only when" icon="check">
    - The pack needs no long-running backend process.
    - All data comes from the platform (the current user, org-scoped APIs the shell already exposes) or from third-party APIs called straight from the browser.
    - You need only one window, with no scheduled or background work.
  </Card>
  <Card title="Go full-stack when" icon="server">
    - The pack owns stateful data you don't want to trust to the browser.
    - You need to hold a persistent process (PTY, daemon, subscription).
    - You need server-side secrets that must never touch the frontend.

    → [Full-stack pack pattern](/patterns/full-stack-pack)
  </Card>
</CardGroup>

## Directory shape

```
pack-settings/
├── khal-app.json         # Manifest — no services[] entry and no frontend.package
├── package/
│   ├── src/index.tsx     # Default export: a React component
│   ├── tsup.config.ts    # CJS + ESM + .d.ts build
│   └── package.json      # Private workspace package
├── package.json          # Workspace root
└── .github/workflows/    # CI checks only; no npm publish workflow
```

No `service/`. No `helm/`. No `Dockerfile`. The pack lives entirely in the browser.

## Manifest

<CodeGroup>
```json khal-app.json (frontend-only)
{
  "$schema": "https://raw.githubusercontent.com/khal-os/app-kit/dev/packages/types/src/khal-app-schema.json",
  "kind": "app",
  "id": "settings",
  "name": "Settings",
  "version": "1.0.0",
  "icon": "./package/src/assets/icon.svg",
  "description": "User preferences and workspace settings",
  "author": "KhalOS Core Team",
  "defaultScope": "user",
  "allowedScopes": ["user", "shared"],
  "permissions": ["user:read", "user:update"],
  "bundlePath": "package/dist/index.mjs"
}
```
</CodeGroup>

The `backend` and `services` keys are simply absent. The platform infers "frontend-only" from their absence.

## Typical SDK usage

Frontend-only packs reach for one hook: [`useKhalAuth()`](/sdk/useKhalAuth) — exposes the current `userId`, `orgId`, `role`, `permissions`, and a `loading` flag. React state handles everything else. Reach for `useNats` only when you want to broadcast user-visible events to other packs (e.g., "theme changed").

```tsx
import { useKhalAuth } from '@khal-os/sdk/app';

export default function SettingsPack() {
  const auth = useKhalAuth();

  if (!auth || auth.loading) {
    return <p>Loading…</p>;
  }

  return (
    <div>
      <h2>Signed in as {auth.userId}</h2>
      <p>Org: {auth.orgId}</p>
      <p>Role: {auth.role}</p>
    </div>
  );
}
```

<Note>
The SDK does not expose a `signOut` method — sign-out is a desktop-shell concern, not a pack concern. The user signs out of KhalOS itself, not out of an individual pack. See [`useKhalAuth`](/sdk/useKhalAuth) for the full contract.
</Note>

## Install

<Steps>
  <Step title="Push to git">
    Push the pack repo or branch that contains `khal-app.json` and the built frontend bundle inputs.
  </Step>
  <Step title="Install from git">
    A customer admin installs the pack from the git URL/branch through Marketplace/App Store or the current CLI install path.
  </Step>
  <Step title="Load in the shell">
    The shell reads the kernel registry row and loads the built bundle for that install.
  </Step>
</Steps>

<Note>
Frontend-only packs ship faster than full-stack ones because there is no service container or Helm chart. Keep the pack frontend-only unless you need server-side behavior.
</Note>
