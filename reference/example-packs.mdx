The fastest way to build a new pack is to read one that already works, then copy only the current git-native contract. Some older pack repos may still contain legacy npm-oriented fields while they are being migrated; do not copy those fields into new packs.

<Callout type="warning">
  **Do not copy legacy publishing fields.** New pack repos are git-native: no `.npmrc`, no `publishConfig`, no publish scripts/workflows, and no package identity in `khal-app.json`.
</Callout>

## Reference map

| Pack | Shape | Why you'd read it |
|---|---|---|
| [`pack-reference-app`](/patterns/design-system-reference-app) | Design-system reference pattern | Launch-safe docs pattern for manifest, scopes, UI consistency, install QA, and what to copy vs not copy. |
| [`pack-notes`](https://github.com/khal-os/pack-notes) | Frontend-only (public) | Clean data-model example and public source. |
| `pack-settings` | Frontend-only | `useKhalAuth`, React state, no service. Treat older manifest snippets as legacy if they show npm-era fields. |
| `pack-terminal` | Full-stack | PTY over NATS, service-owned state, frontend/service subject contract. |
| `pack-files` | Full-stack + storage | Permissions, file access, backend config, and storage concerns. |
| `pack-hello` | Bundle | Multi-app bundle pattern with a shared backend. |

## What patterns to copy

| Want | Look at | Copy this pattern |
|---|---|---|
| Minimal pack, no backend | `pack-notes` / `pack-settings` | permissions, scope, `bundlePath`, and no backend |
| Full-stack with one service | `pack-terminal` | permissions plus backend service shape |
| Permission-heavy pack | `pack-files` | permissions grow with what you touch (filesystem, PTY, network) |
| Customer-scoped deployment | Your customer's install flow | use per-customer config/env; do not hardcode customer identifiers in public docs |
| Multi-frontend suite | `pack-hello` | only use `apps[]` when the install contract for bundles requires it |

## How to use these

1. Start with `khal new app <name>` for a fresh scaffold.
2. Read the closest reference pack for component/service patterns.
3. Copy the manifest shape above, not legacy npm-era fields from old repos.
4. Run build/typecheck/tests and the pack-install policy check before PR review.

<Note>
If a real pack repo still differs from these snippets, treat that as a migration status issue and ask for product/schema review before copying the old shape.
</Note>
