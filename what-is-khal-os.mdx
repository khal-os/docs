Khal OS is a browser-based, macOS-inspired operating shell where **packs** — self-contained apps — run side-by-side for humans and agents. You author packs against the `@khal-os/*` SDK, wire them over NATS, and ship them into customer organisations through a git-native release and catalog flow.

## A pack is the unit of everything

Every pack is a git repo containing a manifest, a frontend bundle source, and optionally a backend service and Helm chart. Some packs use only the frontend. Others wire up a full backend. A few bundle several frontends under one manifest.

<Warning>
Packs are installed from git. Do not publish or install `pack-*` repos through npm or GitHub Packages. The npm packages in the Khal OS ecosystem are framework/CLI packages such as `@khal-os/sdk`, `@khal-os/ui`, `@khal-os/types`, and `@khal-os/app-kit`.
</Warning>

<Tabs>
  <Tab title="Frontend-only (settings-style)">
    ```json khal-app.json
    {
      "$schema": "https://raw.githubusercontent.com/khal-os/app-kit/dev/packages/types/src/khal-app-schema.json",
      "kind": "app",
      "id": "settings",
      "name": "Settings",
      "version": "1.0.0",
      "description": "Desktop settings — appearance, services, keyboard shortcuts, system configuration.",
      "author": "KhalOS Core Team",
      "icon": "./package/src/assets/icon.svg",
      "defaultScope": "user",
      "allowedScopes": ["user", "shared"],
      "permissions": ["nats:subscribe", "nats:publish", "system:clipboard"],
      "bundlePath": "package/dist/index.mjs"
    }
    ```
    No `backend` block. Scaffolds UI only. Installs from the pack git repo.
  </Tab>
  <Tab title="Full-stack (terminal-style)">
    ```json khal-app.json
    {
      "$schema": "https://raw.githubusercontent.com/khal-os/app-kit/dev/packages/types/src/khal-app-schema.json",
      "kind": "app",
      "id": "terminal",
      "name": "Terminal",
      "version": "1.0.0",
      "icon": "./package/src/assets/icon.svg",
      "description": "PTY terminal emulator for KhalOS with NATS-bridged stdin/stdout",
      "author": "KhalOS Core Team",
      "defaultScope": "user",
      "allowedScopes": ["user", "shared"],
      "permissions": ["pty:spawn", "nats:publish", "nats:subscribe"],
      "bundlePath": "package/dist/index.mjs",
      "backend": {
        "image": "ghcr.io/khal-os/pack-terminal-service",
        "helmChart": "oci://ghcr.io/khal-os/charts/pack-terminal",
        "env": { "KHAL_PTY_SHELL": "/bin/bash" },
        "ports": [8002]
      }
    }
    ```
    Frontend `useNats()` subscribes to PTY output; the service owns the PTY and publishes stdout.
  </Tab>
  <Tab title="Bundle (multi-app style)">
    ```json khal-app.json
    {
      "$schema": "https://raw.githubusercontent.com/khal-os/app-kit/dev/packages/types/src/khal-app-schema.json",
      "kind": "app",
      "id": "hello",
      "name": "Hello Bundle",
      "version": "1.0.0",
      "description": "KhalOS Hello demo bundle — multiple frontend apps plus a voice engine",
      "apps": [
        { "id": "hello-console", "name": "Hello Console" },
        { "id": "hello-agent-manager", "name": "Hello Agent Manager" },
        { "id": "hello-flow-designer", "name": "Hello Flow Designer" },
        { "id": "hello-sac", "name": "Hello SAC" }
      ],
      "backend": {
        "image": "ghcr.io/khal-os/pack-hello-voice-engine",
        "helmChart": "oci://ghcr.io/khal-os/charts/pack-hello"
      }
    }
    ```
    A single manifest can declare a suite. Follow the current bundle install contract for per-app bundle routing.
  </Tab>
</Tabs>

## The platform contracts

Every pack consumes a handful of platform contracts. You don't build them — you call them.

| Capability | Your surface |
|---|---|
| **Auth** | [`useKhalAuth()`](/sdk/useKhalAuth) returns `{userId, orgId, role, permissions, loading}` |
| **Window management** | The shell launches, sizes, persists, and restores your pack's windows |
| **NATS** | [`useNats()`](/sdk/useNats) gives you a bridged client; subjects are scoped to your pack's namespace |
| **Services** | [`useService()`](/sdk/useService) calls into your own backend service over NATS |
| **Secrets and config** | Declare `env[]` entries in `khal-app.json`; the platform injects values at install time |
| **Multi-tenant isolation** | Every pack runs inside its org's boundary — permissions, data, NATS subjects |

<CardGroup cols={2}>
  <Card title="Agents are peers" icon="robot">
    Every pack exposes the same SDK to agents and humans. An agent can open your pack, drive its UI, and call its services — no separate API surface.
  </Card>
  <Card title="Packs are composable" icon="grid">
    Packs can publish to NATS subjects other packs subscribe to. A notes pack that emits changes is readable by a search pack, a voice pack, a summarizer pack — without coordination.
  </Card>
</CardGroup>

## The release pipeline

From `git push` to a shipped app, the pipeline is the same for every pack:

<Steps>
  <Step title="PR to `dev` or `main`">
    CI runs typecheck, lint, tests, builds, and validates `khal-app.json` against the schema. Pack policy checks reject npm-publish metadata.
  </Step>
  <Step title="Merge the reviewed git revision">
    The pack repo now contains the manifest, frontend bundle inputs, optional backend service, and optional Helm chart sources the platform can install.
  </Step>
  <Step title="Build service artifacts when needed">
    Frontend code stays part of the git-native install path. If the pack declares a backend, CI may build a service container image and chart for the platform to deploy.
  </Step>
</Steps>

See [Publish your pack](/release/publish-your-pack) for the CI workflow map and failure modes.

## The catalog

Published packs are indexed by the platform's **catalog** — the component that turns a reviewed git source into a one-click install for customer admins. From the platform side:

- Every pack is registered with its manifest, version, permissions, and git source after review/release.
- Customers browse the catalog per-organisation, see the packs they're entitled to, and install them with one action.
- Cross-org distribution is the catalog's problem, not the FDE's. You hand off reviewed git sources; the catalog routes.

On the FDE side, this means: do a good job on `khal-app.json` (accurate permissions, clear `env[]`, real description) and your pack lands cleanly in every customer's catalog. Nothing else is required.

See [Customer install](/release/customer-install) for the customer-side handoff contract — what you hand over after publish.
