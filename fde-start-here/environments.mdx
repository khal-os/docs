title: "Environment ladder for new FDEs"
description: "Understand local, mirrored dev-local, shared dev, customer HML, and production before running deploy commands."
---

KHAL has multiple environment rungs. The same command can be harmless in `local` and dangerous in production, so every proof must name the target.

## Rungs

| Rung | Target | Who uses it | Mutation rule |
| --- | --- | --- | --- |
| 1 | `local` / `dev-local` | You and your agent | Safe for iteration after local proof |
| 1a | mirrored `dev-local` | Agents on a remote code host | Mirror only; not shared k8s truth |
| 2 | shared `dev` | FDEs after local validation | Dry-run first, then scoped mutation |
| 3 | customer dev / HML | Customer-specific validation | Stakeholder/operator gate required |
| 4 | production | Operators | Explicit approval and rollback plan required |

## CLI identity checks

```bash
khal target list --json
khal context --target dev --text
khal doctor --target dev
```

Before a mutating command, the CLI should make these facts obvious:

- target name;
- runtime mechanism;
- source repo/ref;
- manifest identity;
- settings/secrets requirements;
- mutation policy;
- rollback or undo command.

## Dry-run first

```bash
khal install <private-khal-gitea-repo-url> --branch <branch> --target dev --scope shared --dry-run --json
```

Only proceed when the dry-run passes and your agent can explain the evidence.

## When to stop

Stop and ask for operator help if:

- the target resolves to customer/HML/prod and you do not have an approval;
- secrets or App Settings are missing;
- you cannot tell whether the command mutates;
- logs contradict the CLI summary;
- your agent is relying on stale memory instead of current command output.
