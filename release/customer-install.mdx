Once your pack has a reviewed git revision, a customer admin installs it into their Khal-OS instance. This page intentionally stays thin: **the FDE's job ends at a reviewed git handoff; the customer's job begins at install.**

## What the customer needs from you

<Card title="The install source" icon="code-branch">
  - **Git repository URL** for the pack/app repo.
  - **Branch, tag, or commit** that was reviewed and released.
  - **Manifest path** if it is not the repository root `khal-app.json`.
  - **Backend image/chart references** only if the pack declares a backend service.
</Card>

<Warning>
Do not hand off a pack npm package name. Pack/app repos are installed from git; `@khal-os/sdk`, `@khal-os/ui`, `@khal-os/types`, and `@khal-os/app-kit` are framework/CLI dependencies, not customer install artifacts.
</Warning>

## What the customer needs to configure

If your pack declares `env[]` entries in `khal-app.json`, the customer admin supplies values at install time:

<CodeGroup>
```json khal-app.json env block
{
  "env": [
    {
      "key": "MY_EXTERNAL_API_KEY",
      "description": "API key for the third-party analytics service",
      "required": true,
      "type": "secret"
    },
    {
      "key": "FEATURE_BETA_UI",
      "description": "Enable the beta UI variant",
      "required": false,
      "default": "false",
      "type": "boolean"
    }
  ]
}
```
</CodeGroup>

- Entries with `type: "secret"` go into the platform's secret store — the customer pastes a value once, and the platform injects it into your service at runtime.
- Entries with other types become plain config — readable from the admin UI.

<Warning>
**Never hardcode customer-specific values** (URLs, tokens, org identifiers) in your pack source. Declare them in `env[]` so each customer supplies their own.
</Warning>

## What the customer's workflow looks like (summary)

An FDE doesn't run this — but it's useful to understand what happens on the other side so you can hand off cleanly.

1. Admin picks your pack from their platform install UI or runs the equivalent CLI command.
2. Platform clones/fetches the reviewed git revision and reads `khal-app.json`.
3. Admin fills in the `env[]` values the pack declared.
4. Platform builds or locates the frontend bundle, deploys any declared backend service/chart, injects env, and registers the app for the shell.

## Versioning and updates

- Bumping the pack version on the release branch/tag gives customers a new install target.
- Customers opt into upgrades through their platform upgrade flow — not automatic.
- If you break the `env[]` contract (renaming keys, adding required fields), document it in your release notes. Customers need to know before they upgrade.

## What is NOT your problem

- How the customer's platform deploys services.
- How secrets physically land in the container.
- Pod scheduling, resource quotas, ingress routing.
- Cross-pack coordination at the cluster level.

Those are platform concerns, not pack concerns. Stay on your side of the line.
