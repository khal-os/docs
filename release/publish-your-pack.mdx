---
title: 'Publish your pack'
description: 'Push a git-native pack through review, CI, and release without npm-publishing the pack repo.'
---

Publishing a Khal pack starts with a **git push**. Pack identity and install content come from the pack repo and `khal-app.json`; a `pack-*` repo is not published to npm or GitHub Packages.

<Warning>
Do not add `.npmrc`, `publishConfig`, `publish:next`, `publish:latest`, `npm publish`, `pnpm publish`, or `frontend.package` to a pack/app repo. App-kit npm packages such as `@khal-os/sdk`, `@khal-os/ui`, `@khal-os/types`, and `@khal-os/app-kit` are framework/CLI dependencies, not pack distribution artifacts.
</Warning>

## The flow

<Steps>
  <Step title="Open a PR">
    CI runs typecheck, lint, tests, manifest validation, and any service/chart checks declared by the repo. All required checks must pass before merge.
  </Step>
  <Step title="Merge the reviewed change">
    The pack repo now contains the git revision the platform can install from: manifest, frontend source/bundle inputs, optional backend service, and optional Helm chart.
  </Step>
  <Step title="Build release artifacts">
    CI may tag a GitHub Release for the repo. Full-stack packs may also build a backend container image and package a Helm chart. The frontend remains part of the git-native pack install path, not an npm-published `@khal-os/pack-*` package.
  </Step>
  <Step title="Install from git">
    A customer admin installs the reviewed git URL and branch/tag through Marketplace/App Store or the current CLI install path. See [Customer install](/release/customer-install).
  </Step>
</Steps>

<Note>
You never SSH into a customer cluster. You never run `kubectl apply`. You never push images by hand. Your public handoff is the reviewed git revision plus any backend image/chart references the platform needs.
</Note>

## Workflows to expect

New packs should be scaffolded with `khal new`. If you see older `pack-template` language in a historical repo, treat it as implementation history and keep the current git-native policy above.

| Workflow | Trigger | Does |
|---|---|---|
| `ci.yml` | PR to `dev` or `main` | Typecheck, lint, test, build, and manifest validation. |
| `ci-guards.yml` | PR | Secret scanning and repository policy checks. |
| `release.yml` | Push to release branch/tag | Tags or releases the git revision; may build backend service artifacts. |

Customize workflow behavior in your pack repo, but keep pack identity/content in git.

## Versioning

Pack versions live in `khal-app.json` and may be mirrored in `package/package.json` for build tooling. Bump the version in the PR that ships user-visible changes.

<Warning>
Versioning must describe the git revision being installed. Do not use npm dist-tags such as `@next` or `@latest` for pack identity.
</Warning>

## What a merge does not do

- Does **not** deploy to a customer's instance. Customers pull approved git revisions through their own platform flow.
- Does **not** guarantee the new revision is the default. Customers may pin to earlier tags/branches.
- Does **not** invalidate existing users' sessions in the shell.
