Publishing a Khal app is a **git push**, not an npm publish. The CI workflows in a generated app repo validate lint, typecheck, tests, image/chart metadata when present, and release notes. The install source remains the reviewed git repo/ref plus `khal-app.json`.

## The flow

<Steps>
  <Step title="Open a PR">
    The `ci.yml` workflow runs: typecheck, lint, test, `helm lint`, and a check that `khal-app.json` exists. All four must pass before merge.
  </Step>
  <Step title="Merge to `main`">
    The `release.yml` workflow runs on `push: main`. It:
    - Reads the version from `package/package.json`.
    - Tags `v${VERSION}` and pushes the tag.
    - Creates a GitHub Release with auto-generated notes from commits since the previous tag.
  </Step>
  <Step title="Publish release metadata">
    App repos are not published as npm packages. If the app has a backend, CI may publish a service image and chart according to that repo's workflow. The frontend/app identity remains the git repo/ref and `khal-app.json`.
  </Step>
  <Step title="Install">
    A customer admin installs the published version through their platform's install flow. See [Customer install](/release/customer-install).
  </Step>
</Steps>

<Note>
You never SSH into a cluster. You never run `kubectl apply`. You never push a Docker image by hand. Your job ends at "merge the PR". The rest is CI.
</Note>

## Inherited workflows

Generated app repos commonly ship these workflows in `.github/workflows/`:

| Workflow | Trigger | Does |
|---|---|---|
| `ci.yml` | PR to `dev` or `main` | Typecheck, lint, test, Helm lint, manifest validation. |
| `ci-guards.yml` | PR | Secret scanning (gitleaks), `CLAUDE.md` presence check, `CODEOWNERS` check. |
| `release.yml` | Push to `main` | Tag + GitHub Release + version-driven publish. |

Customize behavior by editing these workflows in your pack repo — they're yours, not inherited-at-runtime.

## FDE dry-run before handoff

Before handoff, prove the exact git source/ref with the public CLI:

```bash
khal install <private-khal-gitea-repo-url> --branch <branch> --target dev --scope shared --dry-run --json
```

For the full CLI setup and login flow, see [FDE CLI quickstart](/dev/fde-cli-quickstart).

## Versioning

Pack versions live in `package/package.json` and are the single source of truth. Bump the `version` field in the same PR that merits a release, and `release.yml` will tag + release automatically on merge.

<Warning>
The version must be a **new** version on every merge to `main` that ships user-visible changes. Merging without a bump will cause `release.yml` to fail to re-tag, and customers won't see a new chart version.
</Warning>

## What a merge does not do

- Does **not** deploy to a customer's instance. Customers pull new pack versions through their own platform flow.
- Does **not** guarantee your new pack version is the default. Customers may pin to earlier versions.
- Does **not** invalidate existing users' sessions in the shell.
